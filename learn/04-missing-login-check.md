# ข้อ 4: API ไม่เช็กล็อกอิน หรือเช็กแค่ในหน้าเว็บ

**ภาษาไทย** | [English](04-missing-login-check.en.md)

[กลับไปหน้าลำดับการตรวจ](README.md)

## คำศัพท์

- **ยืนยันตัวตน (authentication)**: ระบบเช็กว่าคุณคือใคร เช่น ล็อกอินด้วยอีเมลกับรหัสผ่าน
- **สิทธิ์ (authorization)**: ระบบเช็กว่าคุณทำสิ่งนี้ได้ไหม เช่น คุณเปิดหน้าแอดมินได้ไหม
- **API**: ช่องทางที่หน้าเว็บหรือแอปมือถือใช้ขอข้อมูลจาก backend เช่น `GET /api/notes` แปลว่าขอรายการโน้ต
- **route หรือ endpoint**: API หนึ่งตัว คือวิธีเรียก (`GET`, `POST`, ...) คู่กับที่อยู่ เช่น `GET /api/notes/export`
- **request**: คำขอหนึ่งครั้งที่ส่งไปที่ API
- **header**: ข้อมูลที่แนบไปกับ request นอกจากตัวเนื้อหา เช่น token ที่บอกว่าคุณคือใคร
- **token หรือ session**: สิ่งที่ระบบให้คุณหลังล็อกอิน แนบไปกับทุก request เพื่อบอกว่าคุณคือใคร ฝั่ง backend จะเก็บไว้ว่า token ไหนเป็นของใคร
- **cookie**: ที่เก็บข้อมูลเล็ก ๆ ในเบราว์เซอร์ เบราว์เซอร์ส่งไปกับทุก request ให้เอง มักใช้เก็บ token
- **frontend**: โค้ดที่รันในเบราว์เซอร์ของคนใช้ ทุกคนเปิดอ่านและแก้ได้
- **backend หรือ server**: โค้ดที่รันบนเครื่องของคุณ คนใช้มองไม่เห็น
- **role**: ระดับของผู้ใช้ เช่น สมาชิกธรรมดา (member) กับแอดมิน (admin)
- **middleware**: โค้ดที่รันก่อน route ทุกตัวหรือหลายตัว ใช้ทำงานที่ต้องทำซ้ำ เช่น เช็กว่าล็อกอินหรือยัง
- **ปฏิเสธไว้ก่อน (deny by default)**: ตั้งให้ทุก route ต้องล็อกอินเป็นค่าเริ่มต้น แล้วเปิดเฉพาะตัวที่ตั้งใจให้คนนอกใช้
- **401 / 403**: รหัสคำตอบของ API 401 แปลว่ายังไม่ได้ล็อกอิน 403 แปลว่าล็อกอินแล้วแต่ไม่มีสิทธิ์
- **DevTools**: เครื่องมือในเบราว์เซอร์ เปิดด้วย F12 หรือคลิกขวาแล้วเลือก Inspect

## ปัญหาคืออะไร

หน้าเว็บดูเหมือนปิดดีแล้ว ยังไม่ล็อกอินก็เด้งไปหน้าล็อกอิน ไม่ใช่แอดมินก็ไม่เห็นเมนูแอดมิน แต่การกันพวกนี้อยู่ใน**หน้าเว็บ** ส่วน **API** ข้างหลังไม่ได้เช็ก หรือเช็กไม่ครบ คนที่เรียก API ตรง ๆ ด้วย `curl` หรือ DevTools จึงข้ามหน้าเว็บไปได้ทั้งหมด

ข้อ 2 คือแอปรู้ว่าคุณเป็นใคร แต่ไม่เช็กว่าข้อมูลเป็นของคุณ ส่วนข้อนี้หนักกว่า คือแอปไม่เช็กแม้แต่ว่าคุณเป็นใคร หรือเชื่อว่าคุณเป็นแอดมินเพราะหน้าเว็บบอกมา

[CWE-306][cwe306] อธิบายปัญหาว่าระบบไม่ยืนยันตัวตนก่อนให้ใช้งานส่วนที่ต้องรู้ว่าใครเป็นคนใช้ ส่วน [CWE-602][cwe602] อธิบายว่า server พึ่งให้หน้าเว็บเป็นคนกัน ทั้งที่การกันนั้นมีไว้ปกป้อง server เอง

## ทำไมอยู่ข้อ 4

- [OWASP Top 10:2025][owasp] หมวด "A01:2025 Broken Access Control" ซึ่งเป็นอันดับ 1 ยกตัวอย่างไว้ตรง ๆ ทั้งการใช้งานเหมือนเป็นผู้ใช้โดยไม่ได้ล็อกอิน การได้สิทธิ์แอดมินทั้งที่ไม่ควรได้ API ที่ไม่มีการกันสำหรับ `POST` `PUT` `DELETE` และการแก้ cookie หรือช่องที่ซ่อนไว้ในหน้าเว็บเพื่อยกระดับสิทธิ์
- [OWASP API Security Top 10 2023][api5] หมวด "API5:2023 Broken Function Level Authorization" บอกว่าฟังก์ชันของแอดมินคือเป้าหลัก และให้ถามว่าผู้ใช้ธรรมดาเรียก API ของแอดมินได้ไหม
- แอปที่ทำกับ AI เจอบ่อย เพราะเราสั่งทีละหน้า "ทำหน้าแอดมิน" "เพิ่มปุ่มดาวน์โหลด" AI ทำหน้าให้ซ่อนปุ่มได้ แต่ route ที่เพิ่มทีหลังอาจไม่มีใครใส่การเช็ก

อยู่หลังข้อ 2 เพราะคนลองเจอง่ายพอ ๆ กัน และบางส่วนเครื่องมือตรวจได้แล้ว

## รูปแบบที่เจอบ่อย

1. **route ที่เพิ่มทีหลังไม่มีการเช็ก** เช่น ปุ่ม "ส่งออก CSV" หรือ "ดาวน์โหลด" ที่ทำเพิ่มทีหลัง ใน Express ถ้าเขียน route ไว้ก่อนบรรทัด `app.use(เช็กล็อกอิน)` route นั้นจะไม่ผ่านการเช็กเลย [เอกสารของ Express][express] บอกว่า middleware ที่โหลดก่อนจะรันก่อน และถ้า route ตอบไปแล้ว middleware ที่อยู่หลังจะไม่ได้รัน
2. **เช็กแค่ในหน้าเว็บ** หน้าเว็บซ่อนเมนูแอดมินหรือเด้งไปหน้าล็อกอิน แต่ API เปิดให้ทุกคนเรียก
3. **เชื่อ role ที่หน้าเว็บส่งมา** เช่น หน้าเว็บเก็บ `role: "admin"` ไว้ในเบราว์เซอร์แล้วส่งไปกับ request หรือ cookie `isAdmin=true` คนใช้แก้ค่าพวกนี้เองได้
4. **เช็กเฉพาะการดู ลืมการแก้และลบ** `GET` เช็ก แต่ `POST` `PUT` `DELETE` ของ route เดียวกันไม่เช็ก
5. **การเช็กที่ผ่านได้ด้วยคำพิเศษ** เช่น เก็บ session ไว้ใน object ธรรมดาของ JavaScript แล้วเช็กด้วย `if (!sessions[token])` object ธรรมดามีชื่อติดตัวมาอยู่แล้ว เช่น `constructor` [MDN][mdn] บอกว่า object มี prototype จึงมี key ติดมาให้ตั้งแต่ต้น ซึ่งอาจชนกับ key ของเรา ส่ง token เป็นคำว่า `constructor` จึงผ่านการเช็กโดยไม่ต้องรู้ token จริง

## ลองกับตัวอย่างก่อน

ต้องมี Node.js กับ `curl` ตัวอย่างนี้เป็น API โน้ตของทีมที่ทำผิดแบบในบทนี้ รันบนเครื่องคุณเท่านั้น ข้อมูลปลอมทั้งหมด token สุ่มใหม่ทุกครั้งที่เปิด ถ้าใช้ Windows ให้รันใน Git Bash

เปิด terminal แรก

```bash
git clone https://github.com/surapas3022/ai-secure-audit.git
node ai-secure-audit/examples/missing-login-check/server.mjs
```

จะเห็น token ของ alice ซึ่งเป็นสมาชิกธรรมดา กับ boss ซึ่งเป็นแอดมิน

เปิด terminal ที่สอง แล้วลองแบบไม่ล็อกอินก่อน

```bash
curl http://127.0.0.1:4200/api/notes
curl http://127.0.0.1:4200/api/notes/export
```

คำสั่งแรกได้ `log in first` ปกติ คำสั่งที่สองได้โน้ตทั้งหมดเป็น CSV ทั้งที่ไม่ได้ล็อกอิน เพราะ route ส่งออกถูกเพิ่มทีหลังและไม่มีใครใส่การเช็ก (รูปแบบที่ 1)

ทีนี้ส่ง token เป็นคำว่า `constructor`

```bash
curl -H "Authorization: Bearer constructor" http://127.0.0.1:4200/api/notes
curl -H "Authorization: Bearer constructor" http://127.0.0.1:4200/api/me
```

ได้โน้ตทั้งหมด และ `/api/me` ตอบว่าคุณชื่อ `Object` เพราะแอปเก็บ session ไว้ใน object ธรรมดา (รูปแบบที่ 5)

สุดท้ายทำตัวเป็น alice (เอา token ของ alice ที่เห็นมาใส่แทน `ใส่token`)

```bash
TOKEN=ใส่token
curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:4200/api/admin/users
curl -H "Authorization: Bearer $TOKEN" -H "X-Role: admin" http://127.0.0.1:4200/api/admin/users
```

คำสั่งแรกได้ `admins only` เหมือนจะกันได้ แต่คำสั่งที่สองแค่เติม header `X-Role: admin` ก็ได้รายชื่อและอีเมลของทุกคน เพราะ API เชื่อ role ที่หน้าเว็บส่งมา (รูปแบบที่ 3)

ปิดเซิร์ฟเวอร์ (Ctrl+C) แล้วเปิดแบบที่แก้แล้ว

```bash
node ai-secure-audit/examples/missing-login-check/server.mjs --fixed
```

เอา token ใหม่ของ alice มาใส่แล้วรันทุกคำสั่งเดิม ส่งออกโดยไม่ล็อกอินและ `constructor` จะได้ `log in first` ส่วน alice ที่เติม `X-Role: admin` จะได้ `admins only` โค้ดที่ต่างกันอยู่ในไฟล์ `examples/missing-login-check/server.mjs` บรรทัดที่เขียนว่า `MISTAKE` และ `FIXED`

ลองให้เครื่องมือตรวจตัวอย่างนี้ด้วย

```bash
node ai-secure-audit/bin/ai-secure-audit.js scan ai-secure-audit/examples/missing-login-check
```

สรุปบนจอจะขึ้น `1 high` เปิดไฟล์ `report.md` ตาม path ที่บอกไว้ จะเห็นว่าชี้ไปที่ `server.mjs` บรรทัดที่เขียนว่า `if (!sessions[t])` ว่าเช็ก session บน object ธรรมดา (รุ่น 0.0.9 ขึ้นไป) แต่ไม่ได้บอกเรื่อง route ส่งออกกับ `X-Role` สองเรื่องนั้นต้องให้คนลอง

## ทำไมเครื่องมือตรวจได้แค่บางส่วน

เครื่องมือไม่รู้ว่า route ไหนตั้งใจเปิดให้คนนอก เช่น หน้าแรกหรือหน้าสมัคร และ route ไหนต้องล็อกอิน เรื่องนี้เป็นกฎของงานคุณ ส่วนที่ตรวจได้คือรูปแบบโค้ดที่ผิดเสมอไม่ว่างานไหน เช่น การเช็ก session บน object ธรรมดา `npx ai-secure-audit` จึงเตือนแบบนั้นได้ และบอกไว้ในรายงานทุกครั้งว่าเรื่องสิทธิ์ส่วนที่เหลือไม่ได้ตรวจ

## ตรวจแอปของตัวเอง

ลองกับแอปที่คุณเป็นเจ้าของหรือได้รับอนุญาตให้ทดสอบเท่านั้น การเข้าระบบของคนอื่นโดยไม่ได้รับอนุญาตอาจผิดกฎหมาย

1. **ทำรายการ API ทั้งหมด** ให้ AI ไล่จากโค้ด (พรอมต์อยู่ข้างล่าง) อย่าดูแค่ที่หน้าเว็บเรียก เพราะ route ที่ไม่มีปุ่มก็ยังเปิดอยู่
2. **เปิด DevTools แท็บ Network แล้วใช้แอปตามปกติ** ด้วยบัญชีแอดมินหนึ่งรอบ และบัญชีธรรมดาหนึ่งรอบ [เอกสารของ Chrome][devtools] บอกว่าแท็บนี้บันทึกการติดต่อเครือข่ายทั้งหมด (ต้องเปิด DevTools ไว้ก่อน แล้วโหลดหน้าใหม่)
3. **คลิกขวาที่ request แล้วเลือก Copy as cURL** เอาไปวางใน terminal แล้วลองตามตาราง โดยลบบรรทัด `-H 'Cookie: ...'` หรือ `-H 'Authorization: ...'` ออกเมื่อจะลองแบบไม่ล็อกอิน

| ลอง | ควรได้ |
|---|---|
| ไม่ล็อกอิน เรียกทุก API ที่ไม่ได้ตั้งใจเปิดให้คนนอก | 401 ทุกตัว รวมถึงส่งออก ดาวน์โหลด และไฟล์ที่อัปโหลด |
| บัญชีธรรมดา เรียก API ของแอดมินที่จดมาจากรอบแอดมิน | 403 |
| บัญชีธรรมดา แก้ค่า role หรือ `isAdmin` ในเบราว์เซอร์ (DevTools แท็บ Application) หรือใน request | ไม่มีผล ระบบใช้ role ที่เก็บไว้ฝั่ง server |
| เปลี่ยนวิธีเรียก เช่น `GET` เป็น `DELETE` หรือ `PUT` | ถ้าไม่มีสิทธิ์ต้องได้ 401 หรือ 403 เหมือนกัน |
| ส่ง token หรือ cookie เป็น `constructor` `toString` `__proto__` | 401 |
| ออกจากระบบแล้วใช้ token เดิม | 401 |

ถ้าไม่อยากไล่เองทั้งหมด ให้ AI ช่วยทำรายการก่อนได้ แต่ต้องลองตามตารางซ้ำ เพราะ AI อ่านพลาดได้

> ทำตาราง route ทั้งหมดในโปรเจกต์นี้ แต่ละตัวบอกว่าต้องล็อกอินไหม ต้องเป็นแอดมินไหม เช็กที่บรรทัดไหน และ role มาจากไหน (ฝั่ง server หรือค่าที่หน้าเว็บส่งมา) route ไหนไม่มีการเช็ก หรือมีการเช็กเฉพาะในหน้าเว็บ ให้บอกก่อน ยังไม่ต้องแก้

## แก้ยังไง

หลักเดียวคือ **backend ต้องเช็กทุก request เอง และปฏิเสธไว้ก่อน** [cheat sheet ของ OWASP เรื่อง authorization][authz] บอกว่าห้ามพึ่งการเช็กในหน้าเว็บ การเช็กในหน้าเว็บมีไว้ให้ใช้งานสะดวกได้ แต่ต้องไม่ใช่ตัวตัดสินว่าให้เข้าหรือไม่ เพราะข้ามได้ง่าย การเช็กจริงต้องอยู่ฝั่ง server

1. **เช็กล็อกอินที่เดียวก่อนทุก route แล้วเปิดเฉพาะ route ที่ตั้งใจให้คนนอกใช้** route ที่เพิ่มทีหลังจะปิดอยู่เองจนกว่าจะมีคนเปิดอย่างตั้งใจ [OWASP API5:2023][api5] แนะนำแบบเดียวกันว่าให้ปฏิเสธทุกอย่างเป็นค่าเริ่มต้น แล้วค่อยให้สิทธิ์ทีละ role

   ```js
   // Every route needs a login, except the ones listed here.
   // sessions is a Map from token to user; req.cookies needs the cookie-parser package.
   const PUBLIC = new Set(['GET /', 'POST /api/login', 'POST /api/signup']);
   app.use((req, res, next) => {
     if (PUBLIC.has(`${req.method} ${req.path}`)) return next();
     const user = sessions.get(req.cookies.session);
     if (!user) return res.status(401).json({ error: 'log in first' });
     req.user = user;
     next();
   });
   // Routes go below this line, never above it.
   ```

2. **เอา role จาก session ฝั่ง server ไม่ใช่จากหน้าเว็บ** เช่น `if (req.user.role !== 'admin') return res.status(403)...` ลบโค้ดที่อ่าน role จาก header, cookie หรือข้อมูลที่หน้าเว็บส่งมา
3. **เก็บ session ใน `Map` หรือฐานข้อมูล ไม่ใช่ object ธรรมดา** [MDN][mdn] บอกว่า `Map` มีแค่ key ที่ใส่เข้าไป จึงปลอดภัยกับ key ที่ผู้ใช้ส่งมา ถ้าจำเป็นต้องใช้ object ให้สร้างด้วย `Object.create(null)`
4. **เช็กทุกวิธีเรียกของ route เดียวกัน** ถ้าใช้ middleware ข้อ 1 จะครอบให้เอง
5. **ให้หน้าเว็บซ่อนปุ่มต่อไปได้** แต่ถือว่าเป็นเรื่องความสะดวก ไม่ใช่การกัน
6. **ลองตามตารางอีกรอบ**

## ดักไว้ล่วงหน้า

- **บอก AI ตั้งแต่ตอนสั่งทำ** เช่น "ทุก API ต้องล็อกอิน ยกเว้นหน้าล็อกอินกับหน้าสมัคร หน้าแอดมินต้องเช็ก role ที่ backend จาก session ไม่ใช่จากค่าที่หน้าเว็บส่งมา" AI ทำตามกฎที่บอกได้ดีกว่ากฎที่ต้องเดาเอง
- **ให้ AI เขียน test ที่เรียกทุก route โดยไม่ล็อกอิน** แล้วต้องได้ 401 ทุกตัวยกเว้นรายการที่ตั้งใจเปิด และเรียก API แอดมินด้วยบัญชีธรรมดาแล้วต้องได้ 403 เวลาเพิ่ม route ใหม่ test จะเตือนถ้าลืม [cheat sheet เดียวกัน][authz] ก็แนะนำให้มี test ของการเช็กสิทธิ์
- **รัน `npx ai-secure-audit` ทุกครั้งก่อนปล่อย** จับการเช็ก session ที่ผ่านด้วยคำพิเศษได้ (รุ่น 0.0.9 ขึ้นไป)

## เรื่องที่เกี่ยวข้อง

- ถ้า API เช็กล็อกอินแล้ว แต่เปลี่ยน id แล้วเห็นของคนอื่น เป็นเรื่องของข้อ 2 [เห็นหรือแก้ข้อมูลของคนอื่นได้](02-other-users-data.md)
- ถ้าหน้าเว็บคุยกับฐานข้อมูลตรง ๆ เช่น Supabase หรือ Firebase การเช็กต้องอยู่ในกฎของฐานข้อมูล เป็นเรื่องของข้อ 3 ใน[ลำดับการตรวจ](README.md)
- route ล็อกอินที่ลองรหัสได้ไม่จำกัดครั้ง `npx ai-secure-audit` เตือนได้ (รุ่น 0.0.5 ขึ้นไป สำหรับ Express และ NestJS)

## ข้อจำกัดของการตรวจแบบนี้

- ลองได้เฉพาะ route ที่รู้ว่ามี จึงต้องให้ AI ไล่จากโค้ดช่วย และ route ที่เขียนไว้แล้วลืมลบก็ยังเปิดอยู่
- แอปที่มีหลาย role เช่น พนักงาน หัวหน้า แอดมิน ต้องลองทุกคู่ ไม่ใช่แค่ธรรมดากับแอดมิน
- เครื่องมือจับการเช็ก session บน object ธรรมดาได้เฉพาะโค้ด JavaScript/TypeScript แบบ Express และเฉพาะเมื่อชื่อที่เก็บดูเหมือน session, token หรือ admin
- ลองผ่านแล้วไม่ได้แปลว่าจะผ่านตลอด เพิ่ม route ครั้งหน้าอาจลืมอีก จึงควรมี test

# ข้อ 2: เห็นหรือแก้ข้อมูลของคนอื่นได้

**ภาษาไทย** | [English](02-other-users-data.en.md)

[กลับไปหน้าลำดับการตรวจ](README.md)

## คำศัพท์

- **ยืนยันตัวตน (authentication)**: ระบบเช็กว่าคุณคือใคร เช่น ล็อกอินด้วยอีเมลกับรหัสผ่าน
- **สิทธิ์ (authorization)**: ระบบเช็กว่าคุณทำสิ่งนี้กับข้อมูลชิ้นนี้ได้ไหม เช่น คุณเปิดดูคำสั่งซื้อเลขนี้ได้ไหม
- **ข้อมูลหนึ่งชิ้น (record)**: ข้อมูลหนึ่งแถวในฐานข้อมูล เช่น คำสั่งซื้อหนึ่งรายการ โปรไฟล์หนึ่งคน
- **id**: เลขหรือรหัสประจำข้อมูลแต่ละชิ้น เช่น คำสั่งซื้อเลข `2`
- **API**: ช่องทางที่หน้าเว็บหรือแอปมือถือใช้ขอข้อมูลจาก backend เช่น `GET /api/orders/2` แปลว่าขอคำสั่งซื้อเลข 2
- **request**: คำขอหนึ่งครั้งที่ส่งไปที่ API
- **token หรือ session**: สิ่งที่ระบบให้คุณหลังล็อกอิน แนบไปกับทุก request เพื่อบอกว่าคุณคือใคร
- **frontend**: โค้ดที่รันในเบราว์เซอร์ของคนใช้ ทุกคนเปิดอ่านและแก้ได้
- **backend หรือ server**: โค้ดที่รันบนเครื่องของคุณ คนใช้มองไม่เห็น
- **เจ้าของ (owner)**: ผู้ใช้ที่ข้อมูลชิ้นนั้นเป็นของเขา
- **BOLA / IDOR**: ชื่อเรียกของปัญหาในบทนี้ BOLA ย่อจาก Broken Object Level Authorization ส่วน IDOR ย่อจาก Insecure Direct Object Reference ความหมายเดียวกัน คือเปลี่ยน id แล้วเข้าถึงข้อมูลของคนอื่นได้
- **DevTools**: เครื่องมือในเบราว์เซอร์ เปิดด้วย F12 หรือคลิกขวาแล้วเลือก Inspect

## ปัญหาคืออะไร

แอปเช็กว่าคุณ**ล็อกอินแล้ว** แต่ไม่เช็กว่าข้อมูลที่ขอ**เป็นของคุณ** คุณเปิดคำสั่งซื้อของตัวเองที่ `/api/orders/1` ลองเปลี่ยนเป็น `/api/orders/2` ก็เห็นชื่อ ที่อยู่ และเบอร์โทรของคนอื่น บางแอปแก้หรือลบได้ด้วย

ไม่ต้องมีฝีมือเลย แค่เปลี่ยนตัวเลข [CWE-639][cwe] อธิบายปัญหานี้ว่าระบบไม่กันผู้ใช้คนหนึ่งเข้าถึงข้อมูลของอีกคน ด้วยการเปลี่ยนค่าที่ใช้ระบุข้อมูล

## ทำไมอยู่ข้อ 2

- [OWASP Top 10:2025][owasp] จัด "A01:2025 Broken Access Control" เป็นความเสี่ยงอันดับ 1 ของเว็บแอป และยกตัวอย่างตรง ๆ ว่าการดูหรือแก้บัญชีของคนอื่นด้วยการส่ง id ของเขา คือปัญหาในหมวดนี้
- [OWASP API Security Top 10 2023][api1] จัด "API1:2023 Broken Object Level Authorization" เป็นอันดับ 1 ของปัญหา API
- แอปที่ทำกับ AI เจอบ่อย เพราะเรามักสั่งแค่ "ทำหน้าดูคำสั่งซื้อ" AI ทำให้ดูได้ แต่ถ้าไม่บอกว่าดูได้เฉพาะของตัวเอง หลายครั้งก็ไม่ได้เช็ก

อยู่หลังข้อ 1 เพราะตรวจด้วยเครื่องมือไม่ได้ ต้องใช้คนลอง

## รูปแบบที่เจอบ่อย

1. **เปลี่ยนเลขในลิงก์หรือใน API** `/orders/1` เป็น `/orders/2`
2. **API เชื่อ userId ที่หน้าเว็บส่งมา** เช่น `GET /api/profile?userId=15` เปลี่ยนเป็น 16 ก็ได้ของอีกคน ทั้งที่ backend รู้อยู่แล้วจาก token ว่าคุณคือใคร
3. **หน้ารายการส่งข้อมูลของทุกคนมา แล้วให้หน้าเว็บกรองเอง** บนจอเห็นแค่ของตัวเอง แต่ข้อมูลที่ส่งมาถึงเบราว์เซอร์มีของทุกคน เปิด DevTools ก็เห็น
4. **ดูได้เฉพาะของตัวเอง แต่แก้หรือลบของคนอื่นได้** เพราะใส่การเช็กแค่ใน API ดู ลืมใส่ใน API แก้และลบ
5. **ไฟล์ที่อัปโหลด** เช่น ใบเสร็จหรือรูปบัตร เปิดได้ด้วยลิงก์ตรงโดยไม่เช็กเจ้าของ

## ลองกับตัวอย่างก่อน

ต้องมี Node.js กับ `curl` ตัวอย่างนี้เป็นร้านค้าจำลองที่ทำผิดแบบในบทนี้ รันบนเครื่องคุณเท่านั้น ข้อมูลปลอมทั้งหมด token สุ่มใหม่ทุกครั้งที่เปิด ถ้าใช้ Windows ให้รันใน Git Bash

เปิด terminal แรก

```bash
git clone https://github.com/surapas3022/ai-secure-audit.git
node ai-secure-audit/examples/other-users-data/server.mjs
```

จะเห็น token ของ alice กับ bob alice เป็นเจ้าของคำสั่งซื้อ 1 และ 3 ส่วน bob เป็นเจ้าของ 2 และ 4

เปิด terminal ที่สอง แล้วทำตัวเป็น alice (เอา token ของ alice ที่เห็นมาใส่แทน `ใส่token`)

```bash
TOKEN=ใส่token
curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:4100/api/orders/1
curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:4100/api/orders/2
```

คำสั่งแรกได้คำสั่งซื้อของ alice เอง ปกติ คำสั่งที่สองได้ของ bob พร้อมที่อยู่และเบอร์โทร ทั้งที่ alice ไม่ใช่เจ้าของ ลองแก้ที่อยู่ของ bob และดูรายการทั้งหมด

```bash
curl -X PUT -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"address":"changed by alice"}' http://127.0.0.1:4100/api/orders/2
curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:4100/api/orders
```

แก้ได้ และรายการมีครบ 4 รายการของทั้งสองคน ส่วนถ้าไม่ใส่ token เลยจะได้ `log in first` แปลว่าแอปนี้**ยืนยันตัวตนแล้ว** แต่**ไม่เช็กสิทธิ์**

ทีนี้ปิดเซิร์ฟเวอร์ (Ctrl+C) แล้วเปิดแบบที่แก้แล้ว

```bash
node ai-secure-audit/examples/other-users-data/server.mjs --fixed
```

token สุ่มใหม่ เอา token ใหม่ของ alice มาใส่แล้วรันคำสั่งเดิม คำสั่งซื้อเลข 2 จะได้ `order not found` แก้ไม่ได้ และรายการเหลือแค่ 2 รายการของ alice โค้ดที่ต่างกันอยู่ในไฟล์ `examples/other-users-data/server.mjs` บรรทัดที่เขียนว่า `FIXED`

## ทำไมเครื่องมือตรวจได้ไม่หมด

เครื่องมือไม่รู้ว่าคำสั่งซื้อเลข 2 เป็นของใคร เรื่องนี้เป็นกฎของงานคุณ ไม่ใช่รูปแบบโค้ดที่ผิดตายตัว `npx ai-secure-audit` จึงบอกไว้ในรายงานทุกครั้งว่าเรื่องนี้ไม่ได้ตรวจ วิธีที่ได้ผลคือให้คนลองด้วยบัญชีสองบัญชี

## ตรวจแอปของตัวเอง

ลองกับแอปที่คุณเป็นเจ้าของหรือได้รับอนุญาตให้ทดสอบเท่านั้น การเปิดข้อมูลในระบบของคนอื่นโดยไม่ได้รับอนุญาตอาจผิดกฎหมาย

1. **สร้างบัญชีสองบัญชี** เรียกว่า A กับ B ใช้เบราว์เซอร์คนละตัว หรือหน้าต่างปกติกับหน้าต่างไม่ระบุตัวตน
2. **ใช้บัญชี A สร้างข้อมูลทุกแบบที่แอปมี** เช่น คำสั่งซื้อ โปรไฟล์ ไฟล์ที่อัปโหลด
3. **เปิด DevTools แท็บ Network แล้วใช้แอปตามปกติ** [เอกสารของ Chrome][devtools] บอกว่าแท็บนี้บันทึกการติดต่อเครือข่ายทั้งหมด (ต้องเปิด DevTools ไว้ก่อน แล้วโหลดหน้าใหม่) จดว่า request ไหนมี id ของข้อมูลอยู่ ทั้งในลิงก์ ใน `?id=` และในข้อมูลที่ส่งไป
4. **เอาลิงก์หรือ request พวกนั้นไปลองด้วยบัญชี B** วางลิงก์ในเบราว์เซอร์ของ B หรือคลิกขวาที่ request แล้วเลือก Copy as cURL แล้วเปลี่ยน token เป็นของ B
5. **ลองทุกการกระทำ ไม่ใช่แค่ดู**

| ลอง | ควรได้ |
|---|---|
| B เปิดข้อมูลของ A | ไม่เห็น (เช่น 404) |
| B แก้ข้อมูลของ A | แก้ไม่ได้ |
| B ลบข้อมูลของ A | ลบไม่ได้ |
| B เปิดหน้ารายการ | ข้อมูลที่ส่งมาใน Network มีแค่ของ B |
| B เปิดไฟล์ที่ A อัปโหลด | เปิดไม่ได้ |
| ไม่ล็อกอินเลย แล้วเปิดลิงก์เดิม | ให้ล็อกอินก่อน |
| เปลี่ยน `userId` ที่หน้าเว็บส่งไปเป็นของ A | ระบบไม่สนค่านี้ ใช้คนที่ล็อกอินอยู่ |

ถ้าไม่อยากทำเองทั้งหมด ให้ AI ช่วยไล่โค้ดก่อนได้ แต่ต้องลองด้วยสองบัญชีซ้ำทุกครั้ง เพราะ AI อ่านพลาดได้

> ไล่ทุก API ในโปรเจกต์นี้ที่รับ id จากหน้าเว็บ ทั้งดู แก้ ลบ รายการ และไฟล์ บอกว่าแต่ละตัวเช็กไหมว่าข้อมูลนั้นเป็นของคนที่ล็อกอินอยู่ เช็กที่บรรทัดไหน ตัวไหนไม่เช็กให้บอกก่อน ยังไม่ต้องแก้

## แก้ยังไง

หลักเดียวคือ **backend ต้องเช็กว่าข้อมูลเป็นของคนที่ล็อกอินอยู่ ทุก request** [cheat sheet ของ OWASP เรื่อง IDOR][idor] บอกให้เช็กสิทธิ์กับข้อมูลทุกชิ้นที่ผู้ใช้ขอ และเช็กทุกครั้งที่มีการเข้าถึง

1. **รู้ว่าใครเป็นคนขอจาก token ไม่ใช่จากค่าที่หน้าเว็บส่งมา** ลบ `userId` ที่รับจากหน้าเว็บออก แล้วใช้ผู้ใช้ที่ได้จาก token แทน
2. **ใส่เจ้าของไว้ในเงื่อนไขค้นหาเลย** แทนที่จะค้นด้วย id อย่างเดียว

   ```js
   // Mistake: finds the order by id only
   db.query('SELECT * FROM orders WHERE id = ?', [req.params.id]);

   // Fixed: the order must also belong to the logged-in user
   db.query('SELECT * FROM orders WHERE id = ? AND owner_id = ?', [req.params.id, req.user.id]);
   ```

   ถ้าไม่เจอให้ตอบเหมือนไม่มีข้อมูลนั้น เช่น 404 [cheat sheet เดียวกัน][idor] แนะนำให้ตอบแบบเดียวกันทั้งกรณีไม่มีและไม่ใช่ของคุณ คนนอกจะได้ไม่รู้ว่ามีข้อมูลเลขนั้นอยู่
3. **ใส่ทุก API ที่แตะข้อมูลชิ้นนั้น** ดู แก้ ลบ ดาวน์โหลด ส่งออก รวมถึงหน้ารายการที่ต้องกรองที่ backend ไม่ใช่ส่งมาทั้งหมดแล้วกรองในหน้าเว็บ
4. **ตั้งค่าเริ่มต้นเป็นไม่ให้** [cheat sheet ของ OWASP เรื่อง authorization][authz] แนะนำให้แอปปฏิเสธไว้ก่อนเป็นค่าเริ่มต้น และห้ามพึ่งการเช็กสิทธิ์ที่ frontend
5. **id สุ่มยาว ๆ ช่วยได้ แต่ไม่พอ** [OWASP API1:2023][api1] แนะนำให้ใช้ id ที่สุ่มและเดายาก แต่ [cheat sheet เรื่อง IDOR][idor] ย้ำว่าถึงจะเดายากก็ยังต้องเช็กสิทธิ์ เพราะ id หลุดได้ เช่น จากลิงก์ที่แชร์กัน
6. **ลองด้วยสองบัญชีอีกรอบ** ตามตารางข้างบน

## ดักไว้ล่วงหน้า

- **บอก AI ตั้งแต่ตอนสั่งทำ** เช่น "ผู้ใช้ดู แก้ ลบได้เฉพาะข้อมูลของตัวเอง เช็กที่ backend ทุก API" AI ทำตามกฎที่บอกได้ดีกว่ากฎที่ต้องเดาเอง
- **ให้ AI เขียน test ที่ใช้สองบัญชี** ให้ B ลองเปิด แก้ ลบของ A แล้วต้องไม่ได้ เวลาแก้โค้ดภายหลัง test จะเตือนถ้าการเช็กหายไป
- **ทำการเช็กไว้ที่เดียว** เช่น ฟังก์ชันหาข้อมูลที่ใส่เงื่อนไขเจ้าของเสมอ ดีกว่าเขียนเช็กกระจายทุกที่แล้วลืมบางที่

## เรื่องที่เกี่ยวข้อง

- ถ้าแอปให้หน้าเว็บคุยกับฐานข้อมูลตรง ๆ เช่น Supabase หรือ Firebase การเช็กเจ้าของต้องอยู่ในกฎของฐานข้อมูล เป็นเรื่องของข้อ 3 ใน[ลำดับการตรวจ](README.md)
- ถ้า API ไม่เช็กแม้แต่ว่าล็อกอินหรือยัง หรือเช็กแค่ในหน้าเว็บ เป็นเรื่องของข้อ 4

## ข้อจำกัดของการตรวจแบบนี้

- ลองได้เฉพาะ request ที่คุณเห็น API ที่หน้าเว็บไม่ได้เรียกแต่ยังเปิดอยู่จะหลุดไป ให้ AI ไล่โค้ดช่วย
- แอปที่มีหลายระดับ เช่น พนักงานกับหัวหน้า ต้องลองทุกคู่ ไม่ใช่แค่สองบัญชีระดับเดียวกัน
- ลองผ่านแล้วไม่ได้แปลว่าจะผ่านตลอด แก้โค้ดครั้งหน้าการเช็กอาจหาย จึงควรมี test
